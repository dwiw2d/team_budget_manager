# CLOVA General 파서 인식률 기준선 (before / after)

측정일: 2026-09-18
대상: `supabase/functions/ocr/clova-general.ts` 의 `extract()`
채점기: `node scripts/ocr-bench/score.mjs` (파서는 이번에도 한 줄도 고치지 않았다)

## 어느 커밋을 쟀는지 — 먼저 읽어라

숫자 하나만 보고 "파서 인식률"이라고 옮기면 안 된다. **두 커밋을 쟀다.**

| 열 | 커밋 | 무엇인가 |
|---|---|---|
| **before** | `89e8886` | 상호 규칙 수정 **전**. 첫 기준선(68.7%)을 낸 파서. |
| **after** | `2c7cefd` | 상호 규칙 수정 **후**. 현재 `receipt-tracker-pwa` 본류. |

`after` 는 `84b7ab2`(상호 거름망이 진짜 상호를 버리던 문제)와 `6369bc1`('…스시'·'…장군'이
주소로 오인되던 문제) 두 수정을 포함한다. 이 문서의 모든 before/after 는 이 두 커밋 사이다.

### 카탈로그도 두 벌이다 — 이것도 먼저 읽어라

`.local/receipt-corpus` 는 **wolfeel 워크트리를 가리키는 심볼릭 링크**이고 살아 있다.
첫 기준선을 낸 뒤 수집 작업이 계속 돌아 카탈로그가 **38장 → 135장**으로 늘었다. 그래서
"같은 카탈로그" 라는 전제가 이미 깨져 있었다. 두 벌을 따로 냈다.

- **38장 기준**: 첫 기준선과 똑같은 표본. 68.7% 라는 숫자가 여기서 나온다. 카탈로그의
  **앞 38개 항목**(`001`~`065`)이 그때의 표본과 정확히 일치한다(재측정으로 46/67 재현 확인).
- **135장 기준**: 현재 카탈로그 전부. 지금의 실제 그림.

파서 비교는 38장 기준이 원본과 이어지지만, **지금 파서가 어디쯤인지는 135장 기준을 봐라.**

## 재현 방법

```sh

node scripts/ocr-bench/score.mjs
RECEIPT_CORPUS_DIR=../wolfeel/.local/receipt-corpus node scripts/ocr-bench/score.mjs
node scripts/ocr-bench/score.mjs --json   # 회귀 비교용

# 채점기 자체의 단위 테스트 — 글로브를 반드시 따옴표로 묶어라.
node --test "scripts/ocr-bench/lib/*.test.mjs"
```

> **따옴표 없는 디렉터리 인자는 쓰지 마라.** Node 24 는 `node --test scripts/ocr-bench/lib/`
> 처럼 디렉터리를 주면 그 디렉터리 자체를 테스트 모듈로 읽으려다 `'test failed'` 로 끝난다
> (v24.14.0 확인: `pass 0 / fail 1`). 글로브를 따옴표로 묶어 Node 가 직접 펼치게 해야 한다.

카탈로그가 없으면 이유를 적고 exit 2 로 끝난다. CLOVA·Gemini API 는 호출하지 않는다.

## 3. 상호 규칙 수정은 도움이 됐나

**정답률은 오르지도 내리지도 않았다. 정확히 ±0 이다.** 135장 전체에서 correct 로 바뀐 항목이
0건, wrong 으로 뒤집힌 항목도 0건이다. 뒤집힌 항목이 없으니 적을 id 도 없다. 두 커밋의 제목이
약속한 것("상호 거름망이 진짜 상호를 버리던 문제", "'…스시'가 주소로 오인되던 문제")에
해당하는 표본이 이 카탈로그에 **채점 가능한 형태로는 하나도 없었다** — 회귀는 안 났지만
이득도 측정되지 않았다.

수정이 실제로 바꾼 것은 딱 하나, **조용한 오답 8건을 표시된 오답으로 돌린 것**이다. 이건
`findMerchant` 가 `{value, sure}` 를 돌려주게 바뀌면서, 라벨 없이 사업자번호 숫자 모양만 보고
윗줄을 집은 경우 `sure=false` 로 `weak` 에 들어가게 된 덕이다. 바뀐 8건:
`124`·`308`(`"LOTTERIA"`), `125`(`"총인원 2명 (일반1명, 청소년1명)"`), `126`·`309`(`"영화관 …"`),
`9114`(`"보험부담금② 0"`) 는 값은 그대로인 채 silent → flagged 로만 옮겼고, `310`·`311` 은
`MERCHANT_ROLE` 이 새로 걸러 `"대표 김유나"` 라는 그럴듯한 오답 대신 `null` 을 내게 됐다.
**요약하면 이 수정은 인식률 개선이 아니라 안전장치 개선이다.** 틀린 답을 덜 틀리게 만들지는
못했고, 틀린 답이 사용자에게 조용히 흘러가는 경로를 8개 막았다. merchant 의 조용한 오답이
15건에서 7건으로 절반 이하가 된 건 그 자체로 값어치가 있지만, 68.7%/63.2% 라는 숫자는
**한 자리도 움직이지 않았다.** 숫자를 꾸며서 보고할 것이 없다.

## 5. 99% 까지 무엇을 고쳐야 하는가

**고치지 않았다. 무엇을 고쳐야 하는지만 적는다.**

### 먼저 알아야 할 것: 99% 는 사실상 무결점이다

- **38장 기준 67필드**: 현재 46 정답. 66/67 = 98.5% 로 99% 에 못 미친다. 즉 **67/67 전부**,
  곧 지금보다 **21개를 더 맞혀야** 99% 다.
- **135장 기준 291필드**: 현재 184 정답. 288/291 = 98.97% 로 모자라고 289/291 = 99.3%.
  즉 **105개를 더 맞혀야** 한다(오답 107건 중 105건).

표본이 작아 한 필드가 1.49%p(38장) / 0.34%p(135장)씩 움직인다.

항목끼리 겹치고 026·027 처럼 글자가 아예 없는 표본은 어떤 규칙으로도 못 맞힌다.
**99% 에 닿으려면 107건 중 105건을 고쳐야 하며,
그중 상당수(로고만 있는 상호, 임대인/입점매장 구분, 티켓 겸용 판형)는 2단계 Gemini 보완 없이는
규칙만으로 원리상 불가능하다.** 규칙 개선만의 현실적 상한은 90% 대 초반으로 본다.

## 합성 입력의 한계

이 숫자는 **합성 좌표**로 낸 것이다. 채점기는 카탈로그의 `visible_lines`(사람이 눈으로 읽은
글자 줄)를 `linesToFields()` 로 격자 좌표에 얹어 CLOVA 응답 모양을 만든다. 줄 높이 26,
줄 간격 30, 고정폭 13px, 넓은 공백(2칸 이상)은 좌우 단으로 크게 벌린다. 따라서 **검증되는
것은 파서의 규칙**(라벨 매칭, 정규식, 금액 다수결, 좌우 단 분리)뿐이고, **실제 OCR 이 만드는
잡음은 하나도 재현하지 못한다** — 기울어진 사각형, 글자 오인식, `lineBreak` 묶음이 위→아래
순서가 아니게 뒤섞여 나오는 현상, 들쭉날쭉한 줄 간격은 전부 빠져 있다. 게다가 `visible_lines`
자체가 사람이 잘 읽어 정리한 결과라 OCR 의 첫 단계 실패는 애초에 표본에 없다. 줄 재구성의
진짜 기준은 실제 응답 픽스처 3장(receipt-1/2/3, `supabase/functions/ocr/clova-general.fixtures.ts`)
이고 이 합성 입력은 그 위에 얹는 보조 자다. **여기서 99% 가 나와도 실제 인식률이 99% 라는
뜻이 아니다. 규칙 회귀를 잡는 용도로만 써라.**

## 분모에 대하여

분모는 `truth` 가 null 이 아닌 필드만 센다. 마스킹·저해상도로 사람도 못 읽어 정답이 null 인
필드는 "파서가 못 읽은 것"과 섞이면 숫자가 거짓말을 하므로 분모에서 뺐다. 그래서 분모가
필드마다 다르다. 38장 중 5장(004, 028, 029, 076, 088)과 135장 중 24장은 네 필드가 모두
null 이라 채점에서 통째로 빠졌다.

`paidAt` 의 부분 정답은 정답으로 세지 않았다. 날짜는 맞고 시각만 `00:00:00` 인 경우다
(38장 기준 1건, 135장 기준 12건).
